# goal

Autonomous pursuit of one user objective per session: windowed token accounting, a hard core budget, 3-turn blocked-audit discipline, durable continuations, and declarative views — all through the public SDK.

## Surface

- Tool `get_goal` (`READ`, safe): current goal state, budgets, token/elapsed usage, remaining budget.
- Tool `create_goal` (`SESSION`, never replayed): create a goal; refused while an unfinished goal exists. Objectives must be non-empty; the tool imposes no objective-length rejection.
- Tool `update_goal` (`SESSION`, never replayed): mark the goal `complete`, or propose `blocked` (accepted only on the third distinct logical turn; attempts 1–2 fail while staging the count). Pause/resume/limited transitions are user/system-controlled, not model tools. `complete` is accepted from any non-complete status; `blocked` is accepted from `active`, `usage-limited`, or `budget-limited`, refused from `paused`/`complete`, and repeating the current status is idempotent with no duplicate event.
- Commands (all `busy_gate=False`): `/goal` (`READ`: inspect state and remaining budget with applicable Edit/Pause/Resume/Clear actions; empty state opens creation), `/goal set` (`SESSION`: create or replace; unfinished replacement returns `pending_confirmation` pinned to the existing `goal_id` and status, so usage-only counter changes do not stale it while an identity/status change refuses visibly), `/goal edit` (`SESSION`: edit objective or budget; a finite raise needs known closed-window spend, `token_budget=null` uncaps), `/goal pause` (`SESSION`: valid from active/blocked/usage-limited/budget-limited), `/goal resume` (`SESSION`: re-open a window and re-arm), `/goal clear` (`SESSION`: direct clear, no extra confirmation), `/goal load_objective` (`READ`: return the full objective text exactly once in `data.objective`).
- Views: `goal` (status banner: status, truncated preview, token count), `goal.details` (fields: status, objective, budget, tokens used, elapsed), `goal.form` (create form when empty, edit form otherwise — preserving identity, creation time, usage, and budget). Live Pause/Resume/Clear actions carry the rendered goal identity, status, and state version; a stale action refuses visibly.
- Context: the active goal contributes its prompt in the legacy user role every dispatch; the observer (`usage`, `run_requested`, `invocation_finished`, `run_finished`) attributes spend, binds the pursuing run, and stages budgets/continuations.

## Configuration

Takes no plugin-specific config. `create_plugin` accepts only the product-injected `providers` key and rejects every other config field visibly. See [configuration](../../../../docs/configuration.md) for global config.

## Behavior and limits

- State (`GoalState`, `schema_version 2`, session scope, strict parsing — unknown keys rejected, required fields enforced, unreported metrics stay `None` never `0`; stored `schema_version 1` rows are refused with no migration): identity, pursuing/retired run binding for terminal-fact authority, status (`active | paused | blocked | usage-limited | budget-limited | complete`), objective (inline or spilled), lifetime token/cost/time counters plus window token counters, contiguous dispatch-sequence accounting windows, blocked-turn count, and the objective-edited bit.
- Activation declares `StateSchema(version=SCHEMA_VERSION)` with the goal payload schema; cold startup and hot activation validate every stored copy against that JSON schema, accept the explicit cleared `{}` row, and refuse malformed payloads. Parser-only invariants (window ordering/overlap, at most one open window, artifact ref/SHA pairing) remain first-use checks because they cannot be expressed in the JSON schema.
- Automatic pursuit is single-pending: create/set/resume plus a completed run cancel this owner's pending **and claimed** pursuits before enqueuing one, so exactly one pursue message remains claimable. Replacement/resume may therefore abort a claimed old pursuit; a completed run's own claimed row is settled by the scheduler. Repeated `update_goal` calls for the current status are idempotent and stage no duplicate terminal event; `blocked` is refused from `complete`/`paused`. A user stop releases the core budget only when it actually pauses an active goal; `RunFinished` saves nothing when the state does not change.
- Windowed accounting: an active window opens on create/resume (`start_sequence = tip`) and closes on pause/complete/block at the actual stop sequence; dispatches before creation or during a pause are excluded, while in-flight dispatches arriving after a pause still attribute to their dispatch window. Enforcement is window-scoped (`window_tokens_used` vs `window_allowance`): reaching the allowance means `budget-limited`, unreported window spend means `usage-limited`. In both cases the plugin cancels its own queue and retains the core constraint — it never uncaps an in-flight user budget. An explicit budget edit keeps the live window and re-stages `new_budget − closed-window spend`; a finite edit that is at/below closed-window spend or leaves no tokens for the open window is refused visibly, and a non-active edit follows the same remaining-spend rule as resume. Unknown closed-window spend refuses a finite raise or budgeted resume visibly (uncap or start a new goal — no allowance is invented). Late bills for a closed window tighten the live allowance while active, or update lifetime counters only while paused. Unbudgeted resume clears any stale constraint.
- Goal budget scope: the goal token budget caps **this session's** provider spend only. Child sessions have their own budgets, and delegation chains have their own root-action limits; the goal token budget is not a chain budget. Child spend does not change the parent goal's token counters.
- Core limit stops: when a run finishes with `stop_cause="limit_reached"` (owner token limit, provider-turn cap, root-action cap, or another core limit), an active goal closes its open window at the stop fact's event sequence and becomes `paused`. The plugin cancels its automatic queue and stages `goal_paused` with the stop cause and any typed `budget_exhaustion` payload. It keeps the goal's own token budget/state for a later edit/resume and does not clear the core budget. It does **not** attempt to distinguish its own owner-token cap from another owner's cap in this branch (the typed payload carries no owner identity); normal usage accounting may already have marked its own cap `budget-limited` before the stop. Already complete/paused/limited goals are unchanged.
- Unknown spend is never zero: one unreported dispatch sets every token total to `None` (still accounting reported elapsed/cost), unknown stays unknown across later reports, and unknown cost never poisons known tokens. Elapsed time accumulates measured `elapsed_seconds`; `RunFinishedFact` neither fabricates `0` nor double-counts.
- Objectives above the 4000-character inline-context allowance use immutable `artifact://` storage through scoped services, never workspace writes. This preserves the small-goal per-turn context footprint, not a business or input limit: the complete original, including whitespace and Unicode, remains loadable through `goal.load_objective`. Model access to a spilled objective depends on the files plugin registering the `artifact://` reader/`read` tool; without files the URI is an explicit unavailable resource and the user-facing loader still works. The edit form uses `load_action` for spilled objectives. Only `artifact://` references resolve; workspace paths are rejected. Platform request/transport and view-data bounds still apply and must fail visibly, so this is not a claim of unlimited ingress.
- Blocked discipline: counted at most once per distinct logical turn; reset by any successful non-goal tool call, a clean completed turn with no blocked attempt in it, `goal.resume`, or an objective edit.
- Prompt parity: the active/budget/edited prompts are the legacy goal texts (persistence, no-shrinking, evidence-first, explicit `update_goal status="complete"`, four-point blocked audit), delivered as a user-role contribution; the objective-edited notice is retained until replace/clear, so it repeats in later contexts rather than risk being swallowed by an in-flight dispatch. The notice announces the edit without re-quoting the objective; the immediately following pursue block carries the single full current objective. Nullable counters render as `unknown`, absent budget as `none`, unbounded as `unbounded`.
- Restart/drain: a pending pursuit is durable but is **not** auto-drained by startup, even when `auto_drain` is enabled. It waits for a user run or an explicit `voidcode drain`; with `auto_drain=False` exactly one pending pursuit remains and repeated restart/read does not duplicate it.
- Disabling (via `core.reload`) runs the pure deactivation transform: every open window closes at the owning session's event tip, live statuses become `paused` (`complete` stays), and identity/objective/counters/budget survive unchanged; the paused goal contributes no context and nothing re-arms until an explicit `goal.resume`. Malformed scope/tip/payload refuses visibly instead of resetting.
