# skills

Workspace skill discovery and on-demand loading, plus always-on rule context: the `AGENTS.md` hierarchy with touched-path file rules and the `.voidcode/rules` rulebook.

## Surface

- Reader `skill://<name>` (`READ` through the admitted `read` tool): loads one discovered skill's `SKILL.md` body plus metadata (description, source path, base directory). Unknown names are no-such-resource; disabled names fail visibly; a broken entry answers with that entry's bounded load error and recovery path without affecting healthy skills. If this plugin is disabled the scheme is unregistered (the `read` tool reports an unsupported URI); if `plugins.skills.config.enabled` is false every `skill://<name>` returns no-such-resource. Line `offset`/`limit` page the render (limit capped at 2000 lines); a page that would exceed the resource byte cap is trimmed at a line boundary, and a single overlong line falls back to the shared pager's zero-based `byte_offset`/`byte_limit` mode. Both modes mark truncation, and reads honor the caller's abort signal.
- Command `/skills` (`READ`): lists discovered skills with enabled/disabled/broken state and recovery actions. `/skills show` prepares a selector or accepts a skill name; details include description, source, enabled state, and paged instructions with navigation. Detail offsets count characters and pages adapt to the view byte limit; resource-reader paging remains line/byte based. Disabled details remain browsable while `skill://` refuses disabled bodies. Browsing never enables a skill; configuration changes require admission.
- Context (each provider request that carries plugin context): the skill catalog (gated on `enabled`), touched-path file rules, an optional bounded rule-diagnostics block when rule files were ignored, then the rulebook. The catalog lists `skill://<name>` as the load target and keeps the source path separately; it is metadata only. If the session cannot see the `read` tool, the catalog says bodies cannot be loaded and does not print a `read` instruction. Broken entries are omitted from the catalog and reported in a bounded diagnostics block. Rule context is independent of the skills setting — it ships whether or not skills are enabled.
- Observer on `invocation_finished`: records the workspace paths each finished invocation touched (from committed `resource_paths` in public facts, never tool-name guessing) into recency-ordered session state (most recent 64).

## Configuration

`plugins.skills.config` (strict; unknown keys refused, `providers` accepted and ignored):

- `enabled` (bool, default `false`): skill discovery and the catalog are off unless explicitly enabled. Rule context is unaffected.
- `paths` (array of non-empty strings, default `[".voidcode/skills"]`): skill search roots. Relative paths resolve against the workspace and must stay inside it; absolute paths are trusted as given.
- `config` (array of rules): each rule requires exactly one selector — `name` (exact skill name) or `path` (SKILL.md file or skill directory; relative paths resolve against the workspace) — plus `enabled` (default `true`). A relative path that escapes the workspace is reported as a configuration diagnostic, not a load failure. Disabling an entry quarantines it, including a malformed/unreadable one.

See [configuration](../../../../docs/configuration.md) for global config.

## Behavior and limits

- Discovery rebuilds per call, so new `SKILL.md` files are visible immediately. Each skill is a directory with a `SKILL.md` whose frontmatter carries exactly `name` + `description` (both non-empty; any other key rejected) and a non-empty body. Each entry is loaded independently: malformed YAML, a bad/missing field, invalid UTF-8, an unreadable file, or a cap violation becomes a bounded per-skill diagnostic and never aborts healthy siblings.
- Caps: discovery visits at most 64 candidate `SKILL.md` paths plus one over-cap probe in deterministic order; further candidates are ignored with a bounded configuration diagnostic. A `SKILL.md` is at most 64 KiB, its body 48 KiB, name 128 characters, description 1,024 characters; the catalog is 8 KiB, the diagnostics block 2 KiB, and the total context contribution 64 KiB. Entries that exceed ingestion caps are omitted with their diagnostic; catalog/context cuts are marked in the injected text.
- Both relative search roots and their discovered entries are containment-checked after resolution: a symlinked `SKILL.md` that resolves outside the workspace is a per-skill diagnostic. Absolute roots remain trusted; `~` expands before that classification.
- Duplicate entries reached through overlapping roots are deduplicated by resolved file path and loaded once. Two different files declaring the same skill name are isolated: the deterministic first entry wins, and every later distinct-path duplicate becomes a broken row with a unique `name (duplicate N)` label plus a diagnostic naming both paths. The healthy body remains loadable through `skill://name`; the duplicate is inspectable and quotable by its label.
- File rules: the `AGENTS.md` hierarchy (project root through workspace, `AGENTS.override.md` winning per directory) is capped at 8 files, 12,000 characters before a truncation marker, and 36,000 bytes total. Each file is read with a 64 KiB ingestion cap using a stat + bounded binary read; a larger file keeps only the prefix and reports a visible diagnostic. When the hierarchy exceeds the file cap, the nearest (workspace-local) rules are kept and half the cap is reserved for touched-path rules. Rule files that are unreadable, invalid UTF-8, or resolve outside the trusted project/workspace root are skipped with a bounded context diagnostic instead of failing the turn.
- Rulebook: `.voidcode/rules` Markdown documents (candidate enumeration capped at 64 files plus one probe, 64 KiB ingestion read per file, 12,000-character content with a visible truncation marker, 240-character metadata, 12,000-character total prompt with a visible truncation marker) with `always_apply` content plus `discoverable` names/descriptions/paths. Each document uses legacy line-based `key: value` frontmatter (not YAML): only `name` (optional; defaults to the file stem), `description` (optional; defaults to the first body line), `application` (required; `always_apply` or `discoverable`), `scope` (optional; `workspace` or `repo`, default `workspace`), and `precedence` (optional integer 0–1000; default 100 for `always_apply`, 0 for `discoverable`) are allowed. Unknown or empty keys, duplicate keys, and non-`key: value` frontmatter lines are reported diagnostics; invalid or unreadable documents do not abort the rest of the catalog. When two documents declare the same name, the greater sort key wins: `repo` over `workspace`, then higher precedence, then name. There is no `rule://` reader — discoverable rules publish real paths for ordinary file tools.
- Session state (`schema_version 1`): `cursor_sequence` + `touched_paths` (unique, at most 64). Disabling keeps the payload as-is — plain history with no live resource — so re-enable resumes exactly where it left off.
