Interact with Language Server Protocol (LSP) servers to get code intelligence features.

Use this tool in two modes:
- Position-based lookups: use when you know the exact file and cursor position.
- Symbol/search lookups: use when you need document outline, workspace symbol search, or diagnostics.

Supported operations:
- diagnostics: Read document diagnostics for a file
- goToDefinition: Find where a symbol is defined
- findReferences: Find all references to a symbol
- rename: Preview a symbol rename and return the workspace edit
- codeAction: Return fixes and refactors for a source range
- willRenameFiles: Ask the server for workspace edits required before moving a file
- hover: Get hover information for a symbol
- documentSymbol: Get all symbols in a document
- workspaceSymbol: Search for symbols across the workspace
- goToImplementation: Find implementations of an interface or abstract method
- incomingCalls: Find callers of the symbol at a position
- outgoingCalls: Find calls made by the symbol at a position

All operations require:
- path: The workspace-relative file to operate on

Additional requirements:
- goToDefinition / findReferences / hover / goToImplementation / incomingCalls / outgoingCalls / rename / codeAction require line and character (1-based, in the negotiated position encoding)
- rename also requires newName
- willRenameFiles requires newPath and does not require line/character
- codeAction accepts endLine, endCharacter, and diagnostics; its range defaults to the starting position
- documentSymbol and diagnostics do not require line or character
- workspaceSymbol accepts query; use it when you know a symbol name but not a cursor position
- server is optional; provide it only when you need to force a specific LSP server in a multi-server workspace

- Character positions use 1-based values in the server-negotiated `utf-8`, `utf-16`, or `utf-32` encoding. The runtime advertises all three encodings and synchronizes full document text with `didOpen` / `didChange` when supported. Results include the selected encoding and opened-document version/hash when synchronization is available.
- List-like results accept 1-based `offset` (default 1) and `limit` (default 50, maximum 50). `item_count` is the full result count; `truncated` and `next_offset` indicate another page.
- The complete raw JSON-RPC response is stored in a session-owned `application/json` artifact. Its `voidcode://artifact/<id>` URI is shown in output and exposed as canonical `body_artifact` / `artifacts` metadata; use `read(path=...)` with `offset` / `limit` to retrieve every line page. For a very large single-line value such as hover text, use `byte_offset` / `byte_limit` and continue with `next_byte_offset`. `lsp_response` is not duplicated inline.
- Rename remains preview-only; rendered pages show up to 50 edit ranges, replacement text, and document versions. Read the full response artifact and use its `result` workspace edit with `apply_workspace_edit` to apply changes.
- Large hover text is bounded by the shared tool-output cap; the full LSP JSON response remains available from its artifact.

Guidance:
- Prefer workspaceSymbol first when you know a symbol name but do not know its location yet.
- Prefer documentSymbol when you want a file outline or need to discover functions/classes before a position-based lookup.
- Use goToDefinition / findReferences / hover / goToImplementation only when you already have a precise file position.
- incomingCalls and outgoingCalls depend on call hierarchy preparation internally; you only need to pass the symbol position.
- Do not use LSP for plain text search; use grep or AST search instead.

Note: LSP servers must be configured for the file type. If no server is available, an error will be returned.
